# AI 模型订阅管理后台：第一版设计

日期：2026-10-16
状态：用户已于 2026-10-16 确认本设计文档

## 1. 目标与成功标准

为经营 AI 服务转售业务的个人提供一个网页后台，统一维护上游渠道、商品、客户、购买与续费记录，并通过邮件提示经营者联系客户续费。

成功标准：经营者能够找到客户每项服务的供货来源、实际成本、销售金额及到期时间；同一客户多项服务分别管理；服务器在到期前 3 天、到期当天提醒经营者；历史交易价格不因商品报价修改而改变。

## 2. 用户明确确认的需求

- 只有经营者自己登录后台，客户没有登录入口。首次网页访问在管理员不存在时允许设置唯一管理员账号密码，创建后自动登录并关闭初始化入口；已有账号不能覆盖。
- 使用网页后台，可通过电脑和手机浏览器访问。
- 第一版由经营者手动搜集、录入上游渠道，不自动搜索渠道。
- 商品范围开放：ChatGPT Plus、Pro、Claude、账号、代充、团队席位、API 中转和额度等均可添加。
- 订阅期限支持日、周、月、年及对应数量。
- 到期前 3 天提醒一次，到期当天提醒一次，邮件发给经营者，由经营者联系客户。
- 每笔交易记录采购成本和销售金额，自动计算差价利润。
- 全部按人民币记账。
- 同一个客户可以同时购买多项服务，各项到期时间独立。
- 已确认采用客户、上游商品、交易记录的组织方式，以及首页、客户、上游渠道、商品、交易与订阅、提醒设置六个页面。

## 3. 本文提出的默认业务规则

以下细节用于把范围变成可实现的设计，属于本次文档的建议，随文档一起供用户审阅：

- 一个商品对应一个供货渠道；多个渠道销售同类服务时建立不同商品，可使用相同套餐名称。
- 一个客户可以有多个服务实例，包括同一套餐的多个账号；续费时选择具体服务实例。
- 每笔交易只记录一项商品或服务。一次购买多项服务时分别录入。
- 第一版录入的交易均为已经成交的业务；不处理待付款、分期、应收款或部分付款。
- API 额度手动记录，不自动查询余额或触发余额不足提醒。
- 所有日期、每日统计和提醒任务使用 Asia/Hong_Kong 时区。
- 使用参考报价加成交快照；利润是销售金额减采购成本，不包含未录入的经营费用。

## 4. 第一版范围边界

包含个人登录、渠道档案、可自定义商品、客户档案、多服务管理、购买与续费历史、人民币差价统计、邮件提醒和发送记录。

自动发现渠道、自动采购、支付收款、客户自助页面、自动向微信或 QQ 发消息、上游 API 对接、库存及卡密自动交付、财务报税、复杂退款及部分退款核算均放在后续版本。

这是一套业务管理工具，不承担向客户提供模型推理或 API 网关的功能。

## 5. 页面与主要操作

### 5.1 首页

- 优先展示今天需要联系的客户服务，区分提前 3 天提醒与当天到期。
- 展示未来 3 天到期、今天到期、已经逾期的有效服务。
- 展示本月销售金额、采购成本和差价利润，以成交日期计入。
- 待办可跳转至客户、服务及交易详情；查看待办不会改变邮件发送状态。

### 5.2 客户

- 保存昵称或名称、联系方式、备注。
- 联系方式支持微信、QQ、手机号、邮箱及其他类型，可保存多条。
- 新建客户至少填写名称；联系方式可以后补，缺失时在待办中提示。
- 客户详情显示名下服务、上游来源、最近交易和完整购买历史。
- 支持按名称及联系方式搜索。

### 5.3 上游渠道

- 保存渠道名称、网址、联系人及联系方式、备注、启用状态。
- 查看该渠道下商品及关联成交记录。
- 只保存经营者手动录入的信息；报价、售后承诺均不视为平台核实的事实。

### 5.4 商品

- 保存商品名称、平台、套餐、交付方式、供货渠道、商品链接。
- 保存上游原始商品名、标签、参考采购价、参考售价、报价记录日期及售后备注。
- 平台、套餐、交付方式允许自行填写，不写死供应商行话。
- 支持有期限服务、按额度服务，以及同时有额度和有效期的商品。
- 默认期限由正整数及日、周、月、年组成；API 额度使用数值加自定义单位。
- 质保条件与服务使用期限分别记录。第一版质保以备注保存，不单独发送质保提醒。
- 账号标识只用于区分交付对象，例如邮箱或自定义编号，不保存账号密码、2FA 秘钥、API 密钥。

### 5.5 交易与订阅

- 新购：选择客户和商品，填写实际成交金额、采购成本、成交日期，以及对应服务信息。
- 默认带出商品参考价格，允许修改；保存时将价格及商品描述作为本次交易快照。
- 服务可有开始日期、到期日期、期限数量与单位、额度与单位、账号或席位标识、交付备注。
- 选择开始日期和期限后自动计算到期日期，允许手动调整。
- 同一客户的每个服务实例拥有独立标识；新购相同商品不会自动合并。
- 续费：从已有服务发起，新增交易并更新服务到期日期；不覆盖之前交易的价格或服务期快照。
- 续费默认从原到期日期与本次续费日期中较晚的一天计算新期限，允许手动改为上游确认日期。
- 同一服务换套餐或更换上游时，续费交易可选择新商品，并保留旧交易来源。
- 无有效期额度服务不进入到期提醒；可以独立追加购买额度，累积购买量不等于剩余额度。
- 支持按客户、渠道、商品、成交日期、服务状态及到期日期筛选。
- 交易可以纠错编辑并记录修改时间；提供作废及原因，作废交易不计入金额统计。
- 作废涉及期限变更的交易时，必须同时明确服务保留的到期日期及状态，界面默认带出变更前的值供核对；不静默回滚后续续费。

### 5.6 提醒设置

- 配置经营者的接收邮箱及邮件发送配置，支持发送测试邮件。
- 展示邮件配置状态、最近任务扫描时间、成功和失败记录。
- 默认且固定使用提前 3 天和到期当天两种提醒，第一版不提供任意提醒规则编辑器。
- 每天以汇总邮件列出当日到达提醒节点的服务，减少同一日大量单封邮件。
- 邮件内容包括客户名称、已记录的联系方式、服务名称、识别标识、到期日和后台详情入口。
- 邮件不包含采购成本和利润；经营者在后台查看完整信息。

## 6. 日期和状态规则

- 日、周分别增加对应天数、7 倍对应天数；月、年使用日历加法。
- 月、年计算如果目标月份不存在对应日期，取当月最后一天：例如 2027-01-31 加一个月得到 2027-02-28；2028-02-29 加一年得到 2029-02-28。
- 业务以日期管理，到期日当天标记为“今天到期”，次日起为“已逾期”。第一版不表达上游精确到小时的停服时间。
- 有期限服务状态根据日期展示：未开始、使用中、今天到期、已逾期；另外提供手动结束状态。
- 手动结束的服务不再生成到期提醒；暂停销售商品或停用渠道不影响已有客户服务。
- 到期时间和提醒节点以服务当前记录为准；交易快照用于保留历史。

## 7. 金额和历史记录

- 采购成本及销售金额均以人民币分存储，显示两位小数，避免浮点金额误差。
- 金额允许为零，不能为负；允许销售价低于成本，差价利润展示为负值。
- 每笔差价利润 = 实际销售金额 - 实际采购成本。
- 本月汇总按成交日期及未作废交易计算，包含新购、续费和额度追加购买。
- 不将差价利润描述为扣除全部费用后的净利润。
- 被交易引用的客户、渠道、商品采用归档或停用，保留历史关联；无业务引用的草稿可以删除。
- 第一版退款由作废整笔交易表达，不支持部分退款，也不追踪退款资金是否实际到账。

## 8. 邮件任务与可靠性

- 邮件任务必须在服务器上运行，不能依赖浏览器保持打开或个人电脑在线。
- 每天本地时间 09:00 生成汇总；当日后续扫描可补上新增的当日提醒项目。
- 提前提醒日期为到期日减 3 个日历日；当天提醒日期为到期日期。
- 每个提醒项目以服务 ID、当前到期日、提醒类型建立唯一标识；重复任务不能重复生成同一提醒。
- 汇总邮件由发送批次关联提醒项目；只有确认发送成功后才标记该批次项目已发送。
- 失败邮件记录简要原因，同日自动重试最多 3 次；次日仍未发送的项目在恢复扫描时补发，并明确标识原计划日期。
- 扫描只为已存在且未结束的服务创建提醒；补发必须重新核对当前到期日，已续费产生的旧到期提醒不再发送。
- 后补录入的历史逾期服务不补发录入前的提醒；直接在首页显示逾期状态。
- 变更到期日期后，未发送的旧提醒取消，按新日期生成；已经发送的历史保留。
- 同日续费或结束服务后，实际发送邮件前再次读取服务，排除已经失效的提醒项目。
- 邮件发送失败不能影响客户、交易及订阅的保存；失败在后台持续可见。
- 普通邮件服务在网络超时后可能无法确认实际是否投递；优先使用支持幂等发送的服务，并记录邮件服务返回的消息 ID，不承诺绝对零重复投递。

## 9. 数据关系

- 管理员：唯一使用者，保存登录凭据摘要及个人设置。
- 客户一对多联系方式、一对多服务、一对多交易。
- 上游渠道一对多商品；商品一对多交易。
- 服务归属于客户，关联当前商品、可选到期日期、额度说明、标识及结束状态。
- 交易关联客户、服务、所购商品，保存实际金额、成交日期、服务期及商品来源快照。
- 提醒项目关联服务，保存目标到期日、类型、计划发送日期及处理状态。
- 发送批次关联多个提醒项目，保存尝试次数、发送状态、消息 ID 和错误摘要。

商品描述和报价变化只影响后续录入默认值；已保存交易使用快照。服务记录提供当前视图，交易记录提供购买与续费历史。

## 10. 应用结构与运行

- 使用单体网页应用及关系型数据库；页面、登录校验、业务接口和金额日期规则在同一项目维护。
- 将日期计算、交易与服务变更、提醒生成和邮件发送分成独立模块，便于验证。
- 所有读取与写入业务数据的入口都检查管理员会话。
- 定时任务由部署环境定期调用独立 Python CLI 命令，提醒唯一标识由数据库约束保护。
- 邮件凭据、登录初始化密钥、数据库凭据与定时任务密钥放在服务端配置，不能返回浏览器或写入仓库。
- 邮件发送接口与业务规则分离；具体运行框架、数据库托管及邮件服务在实施计划中按可用环境确定，不增加本设计范围。
- 提供数据库备份与恢复的部署说明；使用托管备份时在部署验收中确认是否实际启用。

## 11. 交互原则

- 界面使用中文；人民币金额统一格式；手机端可完成客户查询和交易录入。
- 从客户详情直接新购或续费，尽量减少重复录入客户资料。
- 到期列表同时显示客户、联系方式、服务和到期日期，便于联系客户。
- 亏损交易允许保存并明确展示负利润。
- 作废交易、结束服务、归档档案等操作展示影响后再执行。
- 必填项错误、保存失败、邮件配置错误均显示可理解的提示。

## 12. 验收场景

1. 新增一个上游渠道和两个商品，保存不同交付方式及参考价格。
2. 新增客户，保存微信与 QQ 两条联系方式，可搜索找到。
3. 同一客户购买两项不同服务，分别显示成本、售价、利润和到期日。
4. 日、周、月、年期限均能正确计算，覆盖月末和闰年，并能手动调整。
5. 修改商品参考报价后，历史交易的实际成本、售价和利润保持不变。
6. 客户提前续费，新增交易并正确延长期限，旧购买记录仍可查看。
7. 已逾期客户续费默认从续费日期计算；同套餐多个账号可单独选择续费。
8. API 额度商品无有效期时不生成到期提醒；有有效期时正常提醒。
9. 到期前 3 天和当天均进入邮件；重复任务执行不重复创建提醒项目。
10. 续费或手动结束服务后，旧未发送提醒被取消；已发送历史仍可查看。
11. 邮件发送失败可查看并重试；任务中断后能补发有效的漏发提醒。
12. 后补录历史逾期服务只显示逾期待办，不发送录入前的历史提醒。
13. 月度汇总与未作废交易的人民币金额一致，能够表示负利润。
14. 未登录访问后台数据或接口被拒绝；手机浏览器能查询客户和录入交易。

## 13. 部署方式修订（2026-10-16）

- 用户明确要求不使用 Docker Compose；本地开发及生产部署均不依赖容器。
- 用户上传 GitHub 后，通过 CI/CD 发布到服务器；默认建议 GitHub Actions，仅生产分支推送并通过测试后发布。
- Linux 服务器原生运行应用，systemd 管理进程和定时提醒；数据与环境配置独立于发布目录，发布不得覆盖业务数据库。
- CI/CD 只负责发布，提醒任务持续在服务器运行。
- 技术栈已于 2026-10-17 确定为 React + Vite + TypeScript 前端、FastAPI + Pydantic 后端、SQLAlchemy + Alembic 数据层及 SQLite；组件化界面、独立请求层与后端业务模块。生产同域部署，Session + CSRF 登录，定时任务仅服务器命令行执行。
- 发送前重检之后发生的续费可能与已开始的邮件投递重叠，普通 SMTP 无法撤回；记录发送快照和统计时间，不承诺跨网络投递与数据库更新绝对原子。
